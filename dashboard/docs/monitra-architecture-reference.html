Purpose & reading guide

This document exists because five different specs (BRD, PRD, FRS, NFRD, SRS) and a set of wireframes all need the same facts about Monitra — and right now those facts live scattered across a codebase, four chat threads, and nobody's memory. This is where they get written down once.

It is organized the way an engineer reads a system, not the way a template expects a product spec to read: what it is, who touches it, how the pieces talk to each other, what data moves through it, and what's actually been built versus proposed. Section 13 maps each part of this document to the formal deliverable it should feed.

Every claim about current state in this document is verified against the actual repository (backend/, dashboard/) as of commit history through the Monitra.Agent scaffold — not aspirational. Where something is planned rather than built, it's labeled planned.
01

Product overview

Monitra is a multi-tenant SaaS platform that lets an organization's HR/admin staff monitor employee work-hour computer activity — application usage, browser usage, idle time, and attendance — and act on what they see, without the employee needing to install or check anything beyond a background agent.

The problem it solves: distributed and hybrid teams give managers no visibility into whether work-hour time is spent productively, and no systematic way to flag and follow up on attendance or distraction issues without manual spot-checks or trust-only policies.

Who buys it: the business decision-maker is typically an HR lead, ops manager, or founder at a small-to-mid size company running distributed or hybrid teams, who is the tenant in this system's multi-tenant model. A platform operator (you) provisions and administers tenants from a separate, higher-privilege console.

How it works, in one paragraph: a platform admin creates a tenant and issues it an installation token. The tenant's admin distributes that token to employees, who run a small Windows agent that registers itself, then continuously reports work-hour activity back to the API. That data rolls up into attendance and productivity reports the tenant's admin/HR views on a web dashboard — and when a report warrants action (a warning, a coaching note, an attendance flag), the admin issues it from that same dashboard and the employee is notified immediately through the agent already running on their machine.

Naming note: the repository is named Monitra; the current README's body copy still says "Workpulse" from an earlier working name. This document standardizes on Monitra — resolve the README before this becomes customer-facing.

02

Scope

Scope for the release this architecture targets (v1) — not everything the product could eventually be.

In scope — v1

  • Platform admin console: create/suspend tenants, issue tenant admins, generate install tokens
  • Tenant admin console: view employees, devices, and activity reports; issue actions/notices
  • Windows desktop agent: registration, idle-time and foreground-app tracking, heartbeat reporting
  • Attendance & productivity aggregation from raw activity events
  • Distraction-alert rules based on app/URL categorization
  • Immediate agent-side notification when an admin issues an action
  • Per-tenant configurable tracking window (default 9am–5pm), work days, idle threshold
  • Strict tenant data isolation, enforced at both API and database layer

Out of scope — v1

  • macOS and Linux agents (Windows only — see §14)
  • Employee self-service web login/portal (agent is the only employee touchpoint)
  • Screenshot capture
  • Keystroke content capture — only counts, per KeystrokeTrackingMode
  • Mobile agent or mobile dashboard app
  • Payroll or HRIS integrations
  • Multi-language / localization
03

Stakeholders & personas

Four distinct actors, three with logins. Getting these right is what the whole auth and isolation model is built around.

Platform · SuperAdmin

Platform Super Admin

You, or your ops team. Provisions tenants, suspends abusive or non-paying accounts, generates install tokens, has no visibility into any tenant's activity data itself — only account-level administration.

Tenant · Owner / Admin

HR / Org Admin

The buyer and daily user. Views reports, manages employees and devices, configures the tracking window, and issues actions/notices. Owner and Admin roles differ only in tenant-management permissions (e.g. billing), not monitoring access.

Tenant · Viewer

Read-only Reviewer

Sees the same reports as Admin but cannot issue actions, manage devices, or change settings — for auditors, junior HR staff, or external consultants with limited access.

Tenant · ITSupport

IT Support

Manages device fleet health — CPU/RAM/disk, resource-heavy apps, agent connectivity, device logs. Deliberately walled off from behavioral/productivity data: fixes machines, doesn't see why someone was idle (see §14).

No login

Employee

The monitored subject, not a platform account. Their touchpoints are the desktop agent's tray icon, inactivity-justification prompts, and break requests — a deliberate v1 decision to avoid standing up a second auth surface (see §14).

04

System architecture

Six deployable pieces across two runtimes: a .NET backend (API, background worker, desktop agent) and a Next.js web frontend, sharing one PostgreSQL database.

Architecture correction (v0.2): the agent was initially scaffolded as a Windows Service. Windows Services run in an isolated system session and cannot show UI to a logged-in user (Session 0 isolation) — so once the product needs to prompt the employee ("why are you inactive?", break-request status), the agent has to run as a normal per-user application that starts at login and lives in the system tray, the way comparable products in this category do it. Background telemetry logic is unchanged; only the hosting model changes.

Functional scope, by module

Grouped the way an FRS would enumerate them — by module, then by capability.

7.1 — Authentication

  • Tenant user login / logout / current-session lookup — built (/api/auth/*)
  • Platform admin login / logout — built (/api/platform/auth/*)
  • Rate limiting on login (5/min) and registration (3/5min) — built
  • Password reset, email verification — planned
  • Session/token revocation — planned

7.2 — Platform administration

  • Create / list / view tenants — built
  • Activate / suspend a tenant — built
  • Create a tenant admin account on behalf of a tenant — built
  • Generate device install tokens for a tenant — built
  • View platform-wide audit log — planned (writes exist, no read endpoint)

7.3 — Device & agent lifecycle

  • Agent self-registration via install token — built (POST /api/agent/register)
  • Agent heartbeat — partial: endpoint accepts idle/app telemetry but only logs it, doesn't persist
  • Device list, suspend, revoke from the dashboard — planned
  • Assign a device to an employee record — planned

7.4 — Monitoring & reporting

  • Ingest and persist activity/browser/idle events — planned
  • Nightly aggregation into attendance & productivity summaries — planned
  • App/URL categorization (productive / distracting / neutral) — planned
  • Distraction-alert rule evaluation — planned
  • Dashboard report views (attendance, productivity, alerts) — planned

7.5 — HR actions & notifications

  • Issue an action/notice against an employee, from a report — planned
  • Real-time push to the employee's agent (SignalR) — planned
  • Agent-side toast notification + acknowledgement — planned
  • Email fallback when the agent is offline — planned
  • Action/notice history, delivery & read status — planned

7.6 — Tenant configuration

  • Work hours, work days, idle threshold, tracking modes, retention days — modeled on Tenant, built as data, planned as an editable settings screen and as anything that's actually enforced
  • Breaks per day, break duration, inactivity warning threshold, escalation rule — planned (TenantPolicy, v0.2)

7.7 — Inactivity justification v0.2

  • Agent detects idle time crossing the tenant's configured threshold, locally and in real time — planned
  • Agent shows an interactive prompt asking for a reason (typed or quick-pick) — planned, requires the tray-app rework (§04, §14)
  • Reason submitted to API, visible to HR/Admin as a reviewable item — planned
  • Unanswered/unjustified prompts are recorded and can feed an EmployeeAction — planned

7.8 — Break requests v0.2

  • Employee requests a break from the tray app — planned
  • Auto-approved against the tenant's daily quota (cached locally so it works offline); inactivity prompts are suppressed for the break window — planned
  • Over-quota requests are logged and visible to HR, without blocking on manual approval — planned

7.9 — Device health & IT tooling v0.2

  • Agent samples CPU/RAM/disk/battery and per-process resource usage — planned
  • Fleet-wide device health list (Healthy / Degraded / Critical) — planned
  • Per-device drill-down: resource trend, top resource-consuming apps, agent connectivity — planned
  • Device log viewer (restarts, errors, connectivity failures) — planned
  • Restricted to the ITSupport role — no visibility into behavioral/productivity data (§14)

Build phases

The order this document recommends, given what already exists and what depends on what.

Phase 0

Identity & tenant admin foundation — done

Auth, tenant CRUD, isolation architecture, dashboard shell, agent scaffold + registration/heartbeat endpoints.

Phase 1

Harden the foundation

Fix migrations (EnsureCreated → Migrate), add session revocation, externalize CORS, add controller-level tests.

Phase 2

Activity data model & ingestion

ActivityEvent/BrowserEvent/IdleEvent schema, batched ingestion, replace heartbeat's log-only stub with real persistence.

Phase 3

Aggregation & reporting

Build out Monitra.Worker, daily summaries, app/URL categorization, distraction-alert rules, real dashboard report views.

Phase 3.5

Agent tray-app rework v0.2

Convert Monitra.Agent from a Windows Service to a per-user tray app before any interactive-prompt feature can be built (§04, §14) — this blocks Phase 4's inactivity/break work and should land right after Phase 2's ingestion pipeline.

Phase 4

HR actions, inactivity & breaks

EmployeeAction + SignalR push + agent toast/ack + email fallback, plus inactivity-justification prompts and auto-approved break requests (§07.7, §07.8).

Phase 4.5

IT tooling v0.2

Device health telemetry, fleet dashboard, per-device drill-down, device logs, ITSupport role (§07.9) — independent of Phase 4's HR-facing work, can run in parallel.

Phase 5

Production infrastructure

Containerization, CI/CD, secrets manager, observability, backups, MSI installer + code signing for the agent.

14

Open decisions & risks

  • Agent hosting model (resolved, v0.2) — originally scaffolded as a Windows Service; corrected to a per-user tray app because Windows Services cannot show UI to a logged-in user (Session 0 isolation), and inactivity/break prompts require exactly that. See §04.
  • Break approval (resolved, v0.2) — auto-approved within the tenant's configured daily quota, not a manual HR approval queue. Over-quota requests are logged for HR visibility only.
  • IT data scope (resolved, v0.2) — the ITSupport role sees device health and logs only, never inactivity reasons or productivity data. Enforced as a distinct authorization policy, not just hidden in the UI.
  • Product naming — repo is "Monitra," README body copy says "Workpulse." Pick one before anything customer-facing ships.
  • Windows-only v1 — decided, to keep agent engineering scoped to one native implementation. Revisit if target customers need macOS.
  • No employee portal v1 — decided, agent is the sole employee touchpoint. Revisit if self-service (viewing one's own attendance) becomes a sales requirement.
  • Legal/consent requirements vary by jurisdiction — employee monitoring law differs by country/state (e.g. two-party consent, works-council approval in parts of the EU). Needs legal review before any customer outside a validated jurisdiction.
  • Browser extension — window-title parsing alone gives weak URL/domain accuracy; a companion extension is likely required to make UrlTrackingMode meaningful, and isn't scoped yet.
  • Code signing — required before the agent can be distributed without triggering AV/EDR/SmartScreen warnings; needs a certificate and a signing step in the build pipeline.
  • Historical secret exposure — a JWT signing key and DB password were committed to git history before being removed from current files; if this repository has ever been pushed anywhere shared, treat both as compromised and rotate them.
